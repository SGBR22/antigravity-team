# ⚡ Antigravity Multi-Agent Governance & Token Economy Rules

These rules govern all agent behaviors, subagent executions, and multi-agent handoffs across the workspace.

---

## 1. 🚨 MANDATORY AUTO-DISPATCH (Автоматическая маршрутизация)

> **КРИТИЧЕСКИЕ ИНВАРИАНТЫ ДЛЯ ВЕДУЩЕГО АГЕНТА И ОРКЕСТРАТОРА:**
> 1. Не выполняйте инженерные расчеты, кодинг или верстку отчетов монолитно в основном контексте!
> 2. При обнаружении предметной области **НЕМЕДЛЕННО** вызывайте соответствующего субагента через `invoke_subagent`.
> 3. **Координатор (`coordinator`) НЕ пишет код и НЕ верстает документы** — он только декомпозирует граф, распределяет потоки и стыкует контракты.
> 4. **Все отчеты и документы создаются ТОЛЬКО агентом `typst-reporter`** — разработчики и расчетчики передают структурированные данные (`results.json` / `results.toon`).
> 5. **Любой визуал, оформление проектов и дизайн-стили создаются ТОЛЬКО агентом `visual-designer`** — программисты (`senior-dev`, `frontend-dev`) занимаются логикой, алгоритмами, CLI и API. При словах «оформить проект», «сделать красиво», «визуальный стиль», «UI/UX» координатор ОБЯЗАН немедленно вызвать `visual-designer`.

## 2. ⚡ Параллельный конвейер со спекулятивными скелетами (Speculative Skeleton Pipelining)

> **ПРАВИЛО ПАРАЛЛЕЛИЗМА:** Не заставляйте зависимых агентов простаивать в ожидании!
> Запускайте независимых разработчиков **ОДНОВРЕМЕННО** в едином массиве `invoke_subagent`.

### Паттерн исполнения:
1. **Предварительный контракт (Data / API Contract)**:
   - Для бэкенда и БД: схемы `design.md`, интерфейсы или `artifacts/ui_data.json`.
   - Для отчетов: `artifacts/calc_results.json` или `results.toon`.
2. **Параллельный старт (Concurrent Fan-out)**:
   - **Lane 1 (БД и Схемы)**: `database-engineer` формирует DDL, миграции и базовые сущности.
   - **Lane 2 (Бэкенд)**: `senior-dev` реализует бизнес-логику и эндпоинты по контракту.
   - **Lane 3 (Фронтенд)**: `frontend-dev` строит клиентскую логику на базе мок-контракта (`mockData`).
   - **Lane 4 (Тесты)**: `test-engineer` параллельно пишет падающие тесты (TDD Red) по сценариям из спецификации.
   - **Lane 5 (UI/Стили / Отчет)**: `visual-designer` или `typst-reporter` готовит каркас оформления, не дожидаясь бэкенда!
3. **Мгновенное сведение (Zero-Lag Join)**:
   - Стыковка компонентов по контракту. Никакого времени простоя!

## 3. 👥 Multi-Dev Consensus Loop (Коллаборативное программирование)

При любых задачах на написание или изменение кода:
1. **Обсуждение решения**: `system-architect` или ведущий разработчик формулирует спецификацию интерфейсов и сценарии.
2. **TDD-цикл с `test-engineer`**:
   - `test-engineer` пишет падающий тест (RED) $\to$ `senior-dev` / `frontend-dev` / `database-engineer` пишет минимальный чистый код (GREEN) $\to$ headless-прогон `pytest -q` / `vitest run`.
3. **Парный контроль**: `code-reviewer` валидирует решение на предмет регрессий, утечек ресурсов (COM-объекты, дескрипторы, открытые сокеты/транзакции).
4. **Приемка**: `code-reviewer` сверяет код с критериями готовности перед подтверждением.

## 4. 📋 Стандарт Spec-Driven Development (OpenSpec SDD)

Для всех нетривиальных доработок и фич экосистема следует протоколу **OpenSpec**:
1. **Explore**: Исследование кодовой базы и существующих спецификаций `openspec/specs/`.
2. **Propose**: Создание ветки изменений в `openspec/changes/<change-id>/`:
   - `proposal.md` — почему делаем и границы scope;
   - `specs/<capability>/spec.md` — дельта требований (`ADDED`, `MODIFIED`, `REMOVED`) с конкретными `#### Scenario:`;
   - `design.md` — архитектурный подход и контракты интерфейсов;
   - `tasks.md` — упорядоченный чек-лист задач для параллельных агентов.
3. **Apply & Verify**: Исполнение задач параллельными разработчиками и сквозная верификация тестами против каждого сценария.
4. **Archive**: Архивирование изменения и синхронизация дельты в живую спецификацию системы.

## 5. 🧭 Триаж: Планировщик, Координатор и Верификатор плана

Для комплексных задач взаимодействие строится по модели:
```

         │
         ▼

         ▼
[3. Верификатор плана (code-reviewer)]: Проверка выполнения КАЖДОГО пункта задач и соответствия сценариям
         │
         ▼
[Финальная сдача пользователю]
```

## 6. 🛡️ Active Token Shield (Экономия лимитов без потери точности)

1. **Direct-Answer Principle**:
   - Никаких вежливых вступлений и преамбул. Сразу результат, план, diff или команда.
   - В цепочке размышлений держите только критические логические выводы.

2. **The "Think in Code" Paradigm (Стандарт Karpathy)**:
   - **Запрещено читать гигантские логи и файлы целиком.**
   - Для анализа данных пишется одноразовый скрипт (5–10 строк) через `run_command`, выводящий компактную сводку ($< 15$ строк).
   - В терминале используйте фильтры: `Select-Object -First 20`, `Select-String`, `grep`.

3. **Дифференциальные ссылки вместо цитирования кода**:
   - При передаче контекста между агентами запрещено копировать полные файлы.
   - Передавайте кликабельные ссылки с диапазоном строк: `[file.py](file:///path/to/file.py#L40-L65)`.

4. **Компактная нотация TOON (Token-Oriented Object Notation)**:
   - Вместо раздутого JSON с кавычками и скобками используйте плотную YAML/TOON-структуру:
     ```yaml
     status: ok
     output: artifacts/calc_results.json
     metrics: C=142.5pF | E_max=4.2kV/mm
     ```

5. **Anti-Loop Circuit Breaker ("Стоп на 2")**:
   - При повторе ошибки 2 раза подряд немедленно остановитесь, сформулируйте причину и смените тактику.
